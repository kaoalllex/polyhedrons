## 1. Что именно является задачей

Строгая целевая конфигурация — замкнутая ориентируемая полигональная поверхность, вложенная в \(\mathbb R^3\), со следующими свойствами:

- ровно 12 плоских граней;
- каждая грань — простой многоугольник;
- каждая пара граней имеет ровно одно общее ребро;
- каждое ребро принадлежит ровно двум граням;
- в каждой вершине сходятся ровно три грани.

Из этого следуют:

\[
F=12,\qquad E=\binom{12}{2}=66,\qquad V=44,
\]

\[
\chi=V-E+F=-10=2-2g,\qquad g=6.
\]

В двойственной триангуляции это ориентируемая триангуляция поверхности рода 6 с 12 вершинами и полным 1-скелетом \(K_{12}\). В каждой грани исходного объекта ровно 11 рёбер — по одному для каждой другой грани.

**Критически важно не смешивать строгую постановку с ослабленной:** «каждая пара граней соприкасается хотя бы по одному ребру» допускает пары с двумя рёбрами. Такие объекты не решают исходную задачу. Например, два новых восьмигранных объекта рода 3 2026 года имеют 20 пар с одним общим ребром и 8 пар с двумя; это полезные контрольные примеры, но не решения задачи на 12 граней.

Условие «ровно три грани в вершине» следует сохранить в явной формулировке. Оно не выводится только из утверждения о попарной смежности граней.

## 3. Что уже можно считать надёжным фундаментом

Ниже использую четыре уровня доказательности:

- **Теорема / доказано:** есть математический аргумент, который можно проверить независимо.
- **Сертифицированное вычисление:** математическая редукция плюс проверяемый SAT/DRAT/LRAT сертификат.
- **Точный свидетель:** сохранённая рационализированная геометрическая конфигурация, проверенная точной арифметикой.
- **Численное наблюдение:** полезно для направления поиска, но не является доказательством.

### 3.1. Классификация 59 комбинаторных типов — фундамент завершён

Две разные реализации перечисления получили 12,144 помеченных ориентируемых решений и 59 классов с точностью до комбинаторной изоморфности. Независимый валидатор затем проверяет каждый объект как триангуляцию:

- 44 треугольника;
- полный граф рёбер \(K_{12}\);
- каждое ребро принадлежит двум треугольникам;
- ссылка каждой вершины — один 11-цикл;
- ориентируемость и \(\chi=-10\);
- 59 типов попарно не изоморфны.

Сверка с двумя внешними списками тоже даёт биекцию. В текущем аудите повторно запущен `check_triangulations.py --selftest`: все 59 записей прошли проверки, все 1,711 пар классов различны, тесты случайной перенумерации и зеркального обращения прошли.

**Статус:** надёжная база для всего дальнейшего исследования. Комбинаторный поиск по существу закрыт; теперь не нужно снова «искать топологии» — нужно решать геометрическую реализуемость конкретных типов.

Ограничение: сама классификация уже известна из литературы (Altshuler–Bokowski–Schuchert, 1996). Новизна проекта здесь — независимое воспроизведение, аудит, машинно-проверяемые данные и удобная вычислительная база, а не открытие числа 59.

### 3.2. Face-plane reduction — центральная математическая редукция

Для каждой грани \(X\) задаётся плоскость

\[
H_X=\{p:n_X\cdot p=d_X\}.
\]

Вершина, соответствующая треугольнику \(XYZ\) двойственной триангуляции, есть пересечение трёх плоскостей. Ребро границ двух граней лежит на линии пересечения этих плоскостей.

Следствия:

- планарность граней выполняется автоматически;
- неизвестны только 12 плоскостей;
- при фиксированном комбинаторном типе геометрические ограничения становятся строгими неравенствами;
- пространство реализаций открыто в пространстве параметров (после удаления вырожденных конфигураций);
- поэтому существование реализации влечёт существование рационального, а после масштабирования — целочисленного сертификата.

Это очень сильная формулировка задачи: вместо оптимизации координат 44 вершин с большим числом равенств проект оптимизирует нормали и смещения 12 плоскостей.

### 3.3. Лемма о запрещённых тройных пересечениях — сильная основа для OM-SAT

В проекте выведена и независимо проверена лемма, позволяющая выразить вложенность через 176 троек граней, которые не являются вершинами двойственной триангуляции. Идея: три плоскости пересекаются в критической точке; если эта точка одновременно попадает в области трёх соответствующих граней, поверхность нарушает требуемое попарное пересечение.

Adversarial review принял доказательство Lemma 5.1 и предикат `IN` после проверки промежуточных случаев. Проведено точное сравнение с прямой геометрической проверкой, включая случай несимплифицированных многоугольных кривых. В журнале зафиксировано более 2.5 млн проверок предикатов с нулём расхождений в тестовой выборке; независимая геометрическая реализация Track 4 также показала ноль расхождений на 149 конфигурациях.

**Статус:** сильная математико-вычислительная основа. Для публикации я бы всё равно вынес доказательство в отдельный аккуратно оформленный текст и попросил внешнего специалиста по ориентированным матроидам/полигональным поверхностям проверить его целиком.

### 3.4. Точный верификатор геометрии — сильный инженерный актив

`ladder_exact.py` проверяет рациональной арифметикой простоту граней, согласованность рёбер и то, что пересечение каждой пары граней ровно совпадает с предписанными общими рёбрами. `verify_solid.py` извлекает карту из solid-first конфигурации и проводит такую проверку.

В этом аудите непосредственно повторно запущены:

- self-test классификации 59 типов;
- проверка solid-first genus-3 объекта;
- независимый positive control по опубликованной конструкции Röst–Vígh 2026 года;
- точная проверка пяти сохранённых genus-3 реализаций type 0;
- точная проверка двух лучших genus-4 попыток.

Нюанс реализации: геометрические коэффициенты из JSON округляются к целым после масштабирования на \(10^9\) (в Gauss-модуле нормали округляются на \(10^6\)). Значит, сертификат точен для рационализированной конфигурации, которую действительно проверяет код, а не для неограниченного исходного числа с плавающей точкой. Это нормальная и полезная схема, но её необходимо прямо описывать в статье.

### 3.5. Positive control на восьмигранном объекте — важная независимая проверка

Из опубликованных плоскостей и циклов граней Röst–Vígh проект восстановил объект и проверил его собственными инструментами:

- \(F=8,V=24,E=36,\chi=-4,g=3\);
- 20 пар граней имеют по одному общему ребру, 8 пар — по два;
- все 8 граней простые;
- все дополнительные пересечения отсутствуют;
- дискретная степень Гауссова отображения равна \(-2=1-g\);
- собственные числа вращения граней равны +1;
- 20 седловых вершин при нижней границе 7.

Это существенно повышает доверие к геометрическому валидатору и Gauss-инструментам на нетривиальном внешнем примере. Однако оно не подтверждает всё OM-SAT-кодирование и не решает случай с 12 гранями.

## 4. Конструктивные результаты: что реально построено

### 4.1. Пять точных genus-3 реализаций типа 0

Все пять сохранённых JSON-конфигураций проверены точной арифметикой:

| Инвариант | Значение |
|---|---:|
| Граней | 12 |
| Вершин | 32 |
| Рёбер | 48 |
| Эйлерова характеристика | −4 |
| Род | 3 |
| Смежных пар граней | 48 из 66 |
| Простых граней | 12 из 12 |
| Лишних пересечений | 0 |

Это настоящие вложенные замкнутые полигональные поверхности рода 3, а не картинки или численные near-miss.

У них есть ещё одна полезная особенность: их комбинаторные карты допускают дальнейшую *топологическую* пристройку ручек в сторону всех 66 пар. В документации проекта это обозначено словом `extendable`.

**Но `extendable` не означает, что найденную геометрию можно непрерывно продолжить до рода 6.** Это означает только, что комбинаторная цепочка потенциально существует. Геометрическое продолжение пока не найдено.

### 4.2. Ещё один genus-3 объект другого комбинаторного типа

Solid-first поиск независимо нашёл ещё одну точную поверхность с 12 гранями, 32 вершинами, 48 рёбрами и 48 смежными парами. Её последовательность степеней вершин двойственного графа отличается от type-0 ladder-объектов, поэтому карты не изоморфны.

Итак, в репозитории есть **как минимум два различных комбинаторных типа точно вложенных 12-гранных поверхностей рода 3**; для одного типа найдено пять геометрических реализаций.

Уже известный в литературе dual регулярной карты R3.2 имеет те же численные параметры \((F,V,E)=(12,32,48)\), но все его грани восьмиугольные; ваши карты имеют иные последовательности степеней. Это аргумент в пользу их отличия от этого конкретного известного объекта, но не полная проверка исторической новизны.

### 4.3. Род 4 — пока не найден

Две лучшие попытки рода 4 перепроверены точно:

| Кандидат | Простые грани | Непростые грани | Плохие пары граней | Вложение |
|---|---:|---:|---:|---|
| `4viol` | 8/12 | 4 | 4 | нет |
| `degenerate` | 10/12 | 2 | 2 | нет |

Это важная коррекция для статистики поиска: внутренний energy counter и точный верификатор считают разные вещи. Название `4viol` нельзя читать как «ровно четыре дефекта геометрии»: в точной проверке есть четыре непростые грани и четыре пары с неправильным пересечением.

Род 4 не является просто «ещё немного не дожатым» родом 3. Причина плато, по-видимому, структурная — см. Gauss degree ниже.

## 5. Самый важный теоретический сдвиг: отображение Гаусса

Для ориентированной замкнутой поверхности степень отображения Гаусса равна

\[
\deg G=\frac{\chi}{2}=1-g.
\]

Для дискретной поверхности проект использует нормали граней и ориентированные треугольники двойственной карты. Каждая ручка в лестнице рода должна изменить требуемый класс степени на −1.

Проект также использует необходимое условие покрытия сферы положительными сферическими треугольниками: для каждого общего направления должна существовать положительная локальная нормальная конфигурация. Из интегрального аргумента по площадям выводится нижняя граница на число седловых треугольников:

\[
s\ge 2g+1.
\]

Важное разграничение:

- степень в выбранном рациональном общем направлении проверяется точными знаками определителей;
- число седловых треугольников также вычисляется точно;
- покрытие сферы в `gauss_gate.py` сейчас проверяется на конечном наборе направлений (64 + дополнительная выборка подтверждения), а не доказывается для всей сферы.

Поэтому текущий `covering=True` — сильный численный фильтр, но сам по себе **не является точным доказательством глобального покрытия**. Для этого нужна точная проверка сферической разметки/разбиения или отдельный комбинаторный аргумент.

### 5.1. Почему род 3 → 4 ломался

У пяти сохранённых type-0 реализаций собственная степень Гаусса равна −2, как и должна быть для рода 3. Для следующего уровня рода 4 нужно −3. Анализ каждого следующего handle показал, что добавляемая ручка в этих фиксированных конфигурациях даёт вклад \(k_\tau=0\), хотя требуется −1.

Следовательно, для этих seed-конфигураций переход на следующий уровень, если держать нормали в том же допустимом классе и не проходить через вырождение, невозможен. Попытки локального улучшения геометрии при неизменном наборе нормалей не могут исправить неправильную степень.

Это объясняет, почему SA, CMA-ES, LNS, штрафы за вырождение и дрейф по смещениям упирались в похожие дефекты. Они оптимизировали внутри области, из которой следующий уровень недостижим без смены класса нормалей.

**Область применимости:** это не доказательство невозможности genus 4 для type 0 вообще, и тем более не доказательство невозможности genus 6. Оно исключает конкретный путь продолжения от найденных genus-3 seeds при указанных нормальных/непрерывных ограничениях.

### 5.2. Новый эксперимент Q1

Для типа 58 поиск за 447 секунд нашёл одну систему из 12 нормалей, у которой все семь уровней цепочки находятся в требуемых классах степени:

\[
(1,0,-1,-2,-3,-4,-5).
\]

Все семь class-checks прошли точную проверку. Но затем точная SMT-задача смещений плоскостей для нижнего уровня — сферы рода 0 — оказалась `UNSAT` за 32.7 секунды.

Это хороший результат, потому что он разделяет два условия:

1. нормали могут находиться в правильном Gauss-классе на всей лестнице;
2. это ещё не гарантирует, что существуют смещения плоскостей, замыкающие простые грани даже на нижнем уровне.

`UNSAT` относится только к найденному набору нормалей, выбранному gauge и заданному подграфу. Он **не исключает** другие системы нормалей для типа 58.

### 5.3. Общая оценка Gauss-подхода

Это самый перспективный новый инструмент проекта. Он объясняет структурные причины неудач старых поисков и создаёт дешёвый prefilter до дорогого точного SMT.

Но в текущей реализации есть граница строгости: степень и saddle count точны, глобальное покрытие — нет. Следующий шаг должен усилить эту часть, а не маскировать выборочную проверку под доказательство.

## 6. Что исключено, что остаётся открытым

### 6.1. Симметричные реализации исключены

Проект перебрал 25 возможных классов нетривиальной симметрии (21 случай с инволюцией типа C2 и 4 случая с симметрией порядка 3). Журналы ночных вычислений фиксируют `UNSAT-VERIFIED` для всех случаев: CaDiCaL построил DRAT, `drat-trim` проверил сертификаты. Внешняя работа Moki–Julio 2026 года формулирует тот же итог: у 12-гранного объекта не может быть нетривиальной симметрии; асимметричный случай остаётся открытым.

В проекте есть ещё более сильный вычислительный результат: исключение симметричного полигонального погружения (без глобальных условий полного вложения) по локальным условиям простоты граней, ограничению числа рефлексных углов и ориентационной согласованности. Если математические предпосылки кодирования корректны, это сильнее простого запрета симметричного вложения.

Однако нужно зафиксировать доказательную цепочку аккуратно:

- DRAT доказывает UNSAT конкретного CNF;
- переход от CNF к геометрическому утверждению требует отдельного доказательства корректности кодирования;
- журналы содержат `cnf_sha256`, `proof_sha256` и строки `DRAT-VERIFIED`;
- крупные `.drat`-файлы исключены из Git через `.gitignore` и отсутствуют в приложенном bundle.

Поэтому на основании bundle можно проверить отчётность, хеши и статус, но нельзя повторно прогнать проверку всех сырых сертификатов без доступа к архиву результатов/машине, где они сохранены. Для публикации сертификаты или долговременный архив доказательств нужно опубликовать вместе с CNF-хешами и инструкцией воспроизведения.

### 6.2. Асимметричный случай остаётся открытым

Это теперь центральная часть задачи. Полное OM-SAT для асимметричных карт пока не закрыто. В журналах есть timeouts — например, первые 8 асимметричных типов не решились за 2.17 часа каждый. Это не `UNSAT` и не свидетельство невозможности; это только недостаточная вычислительная мощность/слабое кодирование на данном этапе.

В проекте пока нет доказательства, что ни одна из 59 карт не реализуема. Также нет кандидата рода 6.

## 7. Сопоставление с современной мировой работой

### 7.1. Классическая база

- Altshuler, Bokowski, Schuchert (1996) — 59 ориентируемых neighborly triangulations рода 6 с 12 вершинами.
- Schewe (2010) — доказал невозможность геометрической реализации *вершинной двойственной задачи* (12 вершин, все пары соединены ребром) с помощью oriented matroids и SAT.

**Не переносить теорему Schewe на вашу задачу по двойственности.** Вложенность пространственных полигональных поверхностей не сохраняется простым двойственным переходом: face-plane задача и vertex realization задают разные условия.

### 7.2. Bokowski–H. (2025): численный поиск по всем 59 типам

В статье *Polyhedral Embeddings of Triangular Regular Maps of Genus g, 2 ≤ g ≤ 14, and Neighborly Spatial Polyhedra* авторы применяют оптимизацию к полигональным вложениям и к двойственным объектам. Для 12 одиннадцатиугольных граней они сообщают, что не нашли вложения ни для одного из 59 типов. Это независимый отрицательный численный результат, но не доказательство невозможности.

Их численный подход близок по духу к ранним веткам проекта: случайные/кластерные старты, оптимизация пересечений, затем улучшение геометрического качества и расстояний. Они также отмечают, что примеры, которые им удавалось находить, часто имели симметрию. Это объясняет, почему симметричные Ansatz были естественной первой целью, но после их исключения надо систематически искать асимметрично.

### 7.3. Moki–Julio (2026): запрет симметрии

Их публичный репозиторий описывает computer-assisted theorem с 36 SAT instances и проверяемыми DRAT-сертификатами: симметричного 12-гранного объекта нет; асимметричный случай не решён.

Ваш проект независимо воспроизводит симметричное исключение своим кодированием. Это ценно, особенно если доказать/показать, что локальное исключение погружения действительно сильнее геометрического запрета вложения. Но для публикации нужно отличить собственно новую математическую часть от независимой репликации уже опубликованного computer-assisted результата.

### 7.4. Pirozhkov: самый важный текущий вычислительный peer project

`pirozhkov-andrei/polyhedraproof` — ещё один актуальный проект именно по задаче 12 попарно смежных граней. Он переводит задачу в 59 булевых формул и строит пайплайн для независимо проверяемых опровержений через cube-and-conquer и LRAT.

По состоянию на опубликованный статус:

- каждая формула имеет 5,257 переменных и 52,177 ограничений;
- проверка доказательств выполняется отдельным `cake_lpr`;
- есть два независимых certifier-а, контроль хешей, контейнеры с зафиксированными версиями инструментов, CI, тесты и журналирование;
- пилот на двух формулах закрыл 31,187 листьев с проверенными LRAT-доказательствами за 648.5 core-hours;
- полная кампания по всем 59 формулам не проведена; оценка порядка 19,000 core-hours является экстраполяцией по двум формулам, а не фактическим замером полной задачи.

Это очень полезный ориентир для уровня инженерии доказуемых вычислений. Я бы не советовал дублировать вслепую их полный 19k-core-hour cube-and-conquer прогон. Лучше сравнить математические редукции и кодировки, найти независимые контрольные теоремы/усиления, предложить cross-check или совместный аудит. Нельзя предполагать, что их формула эквивалентна вашему OM-SAT, не сопоставив точные переменные, предпосылки и soundness clauses.

### 7.5. Новые восьмигранные объекты 2026 года

Ruslan Mizhaev (15 сентября 2026) и Gergely Röst–Viktor Vígh (26 сентября 2026) опубликовали два комбинаторно различных объекта рода 3 с восемью простыми планарными девятиугольными гранями. В каждом случае все пары граней смежны, но восемь пар имеют два общих ребра, поэтому эти примеры не являются строгими pairwise-one-edge объектами.

Их ценность для вас:

- это свежие точные геометрические positive controls;
- они показывают, что новые polyhedral surfaces рода 3 всё ещё находятся;
- Röst–Vígh описывают computational geometric search и демонстрируют восстановление объекта из плоскостей;
- ваш `control_rost_vigh.py` уже успешно проверил опубликованный объект.

Это хороший путь к тестированию лестницы с кратными смежностями, но прежде чем переносить туда Gauss gate и SAT, код должен явно учитывать повторяющиеся рёбра пары граней. Текущая часть `gauss_degree`/`gauss_gate` в ряде функций предполагает простой dual map; в литературном TODO этот пробел уже отмечен.

## 8. Какие результаты уже можно показывать коллегам

### Уверенно можно показывать сейчас

**A. Два точно вложенных genus-3 типа с 12 гранями.**  
Это наглядный и проверяемый результат. Но прежде чем заявлять новизну, нужно провести полноценное сравнение с каталогами известных polyhedral maps и с опубликованной R3.2-конструкцией.

**B. Независимая точная реализация известного Röst–Vígh объекта.**  
Не самостоятельное открытие геометрии, но хороший evidence package, подтверждающий работоспособность проверяющего ядра на реальном новом объекте с кратными смежностями.

**C. Независимая полная проверка 59 комбинаторных типов.**  
Скорее вычислительный артефакт/репликация известной классификации, чем новый математический результат. Но это важная основа и может быть полезна как открытый набор данных и тестов.

**D. Gauss-degree объяснение барьера genus 3 → 4 для сохранённых type-0 seeds.**  
Это, возможно, самая интересная внутренняя теоретическая история: конкретные неудачи оптимизатора оказались следствием неверного топологического класса нормалей. Чтобы сделать это публикационным результатом, нужно оформить точную теорему с условиями и доказательством инвариантности, а затем расширить анализ за пределы пяти seed-ов.

### Потенциально сильный результат после минимальной доработки

**E. Запрет симметричного полигонального погружения.**  
Если доказательство локальных ограничений и полнота симметрийного перебора будут оформлены строго, это может стать отдельным утверждением сильнее «не существует симметричного вложения». Нужно проверить, не покрыт ли этот результат уже более сильной формулировкой Moki–Julio, затем получить raw DRAT certificates и внешнее ревью.

### Что пока нельзя заявлять

- «Мы доказали, что 12-гранного многогранника не существует» — нет.
- «Мы почти нашли genus 6» — нет; genus 3 с 48/66 — не «почти готовый» объект, поскольку нехватающие пары не являются небольшим локальным косметическим дефектом.
- «Правильная степень Гаусса означает, что реализация существует» — нет; Q1 прямо показал обратное.
- «Покрытие сферы доказано точным Gauss gate» — нет, покрытие сейчас тестируется на конечном наборе направлений.
- «Ни один из 59 типов не реализуем» — нет, асимметричный случай остаётся открытым.

## 9. Критика исследовательского процесса: сильные стороны и пробелы

### Что организовано хорошо

1. **Параллельные исследовательские треки.** Комбинаторика, геометрия, oriented matroids/SAT, теория, литература и adversarial verification не перемешаны в одну непрозрачную задачу.
2. **Гипотезы явно фиксируются.** Есть sprint-board, stop-list, experiment-log, review prompts и решения, какие направления прекращать.
3. **Есть контрольные объекты.** Szilassi используется как positive control для n=7; новый Röst–Vígh объект — как независимый контроль для восьми граней и двойных смежностей.
4. **Точный внутренний проверяющий контур.** Кандидат не считается достижением по одной float-energy метрике.
5. **Adversarial review.** Отдельный агент проверял леммы и предикаты, а не только генерировал код.
6. **Отрицательные результаты сохраняются.** В проекте есть stop-list, журналы провалившихся запусков и объяснение, почему некоторые подходы больше не стоит масштабировать.

Это соответствует духу современных практик reproducible computational research: код и данные должны позволять третьей стороне независимо проверить вывод, а окружение, версии и provenance должны быть частью результата. См. The Turing Way и Computing Handbook Kempner Institute.

### Что нужно улучшить

**1. Нет фиксированного вычислительного окружения.**  
В bundle нет `pyproject.toml`, lockfile зависимостей, Dockerfile, Makefile или CI workflow. `HOW_TO_RUN_OVERNIGHT.md` предлагает установить `numpy scipy numba python-sat z3-solver sympy`, но версии не закреплены. Для научного вычисления это серьёзный пробел: solver/version drift может менять производительность, поведение и в редких случаях воспроизводимость.

**2. Нет универсальной команды end-to-end воспроизведения.**  
Есть scripts для отдельных задач, но нет единой команды, которая проверяет data, запускает короткие positive/negative controls, проверяет хеши, пересчитывает ключевые таблицы и собирает итоговый evidence report.

**3. Сырые proof certificates не входят в bundle.**  
В JSONL есть их SHA-256 и отметки проверки, но не сами `.drat` файлы. Для долгосрочного научного результата сертификаты должны храниться в Zenodo/другом архиве или выпуске репозитория с контрольными хешами.

**4. Run provenance неполон и неоднороден.**  
Для каждого запуска должен фиксироваться единый минимум: commit SHA, source hash, map canonical ID, seed, все параметры, версия целевой функции, версии solver-ов и библиотек, ОС/CPU, wall time, core time, exit status, хеш input/output, exact verifier result, и причина остановки.

**5. Несогласованность документации.**  
`literature-review.md` всё ещё говорит, что первичные статьи не были прочитаны и сайты блокировались; более поздний `TODO_world_research_2026.md` говорит, что arXiv уже был доступен и новые материалы прочитаны. Эти документы нужно свести в единую актуальную literature matrix с датой, первичным источником, статусом чтения и точностью утверждений.

**6. Терминология дефектов нуждается в нормализации.**  
Сейчас есть violation events, local defects, nonsimple faces, bad face pairs, class defects и точные ошибки вложения. Их нельзя сводить в один счётчик `violations`. Нужен формальный schema для каждой метрики.

**7. Небольшие технические сбои интерфейсов.**  
`ladder_exact.py` в CLI читает список записей и индексирует его, а некоторые сохранённые примеры genus-ladder — одиночные JSON-объекты с `planes`/`triangles`. Вручную можно вызвать API после получения links, но публичный CLI не универсален. Нужен единый `verify_candidate.py`, который принимает нормализованный JSON любого поддерживаемого типа.

**8. LLM/subagents не заменяют независимую экспертизу.**  
Роли «генератор — критик — adversarial verifier» полезны для покрытия пространства идей. Однако три агента, работающие на одном и том же исходном коде и с похожими предпосылками, не являются тремя независимыми научными рецензентами. Перед theorem-level публикацией нужен человеческий математический review вне текущей цепочки агентов, особенно по Lemma 5.1, глобальным Gauss-критериям и SAT soundness.

## 10. Что стоит прекратить, а что оставить

### Остановить или резко ограничить

- Новые большие прогоны black-box SA/CMA/GA по старой violation-функции без структурного фильтра. Уже известно, что лучшие near-miss seeds не проходят Gauss prefilter и локально далеки даже от immersion.
- Попытки продолжать именно пять старых type-0 genus-3 конфигураций к genus 4 с теми же нормалями. Gauss-класс уже показывает, почему этот путь блокирован.
- Torus-period relaxation как основной маршрут. Нулевой дефект периодов был получен на конфигурациях с непростыми гранями; после добавления простоты задача оказалась infeasible для проверенных примеров.
- Увеличение весов/порогов/итераций на прежней objective function, если эксперимент не меняет математическую гипотезу или допустимое пространство.

### Продолжить

- Генерировать новые системы нормалей под Gauss degree на нескольких разных combinatorial ladders, а не только вокруг одного старого seed.
- После каждого набора нормалей немедленно решать exact offset feasibility, начиная с нижнего уровня; не тратить время на подъем цепочки, если M0 не реализуем.
- Использовать локальную immersion-модель. Если для какого-либо типа доказано, что даже погружение с простыми гранями невозможно, вложенность автоматически исключается. Это может дать более дешёвые UNSAT-инстансы.
- Продолжить анализ handle-local invariants: \(k_\tau\), admissible gauges, saddle count, turning numbers, hemisphere margin. Записывать каждый из них отдельно.
- Сохранить solid-first как источник новых partial embeddings и независимых genus-3 топологий, но оценивать его как отдельный генератор, не как прямой маршрут к genus 6.

## 11. Рекомендуемая программа следующих экспериментов

### Фаза 0. Заморозить формальную постановку

Создать единый `SPEC.md` с:

- строгой целью и всеми локальными условиями;
- отдельным описанием ослабленных постановок с кратными общими рёбрами;
- разрешёнными/запрещёнными вырождениями;
- соглашением об orientability, простоте граней и general position;
- определениями всех счётчиков и статусов доказательности.

**Результат фазы:** никакой неоднозначности, что именно является решением.

### Фаза 1. Укрепить воспроизводимость

Минимальный план:

- `pyproject.toml` или lockfile с точными версиями Python-библиотек;
- Docker/Apptainer image с закреплёнными SAT/SMT solver-ами и проверяющими;
- CI: selftest 59 карт, Szilassi positive control, Röst–Vígh positive control, genus-3 exact witnesses, отрицательные мутанты;
- одна команда `make verify-all` / `python -m polyhedrons.verify_all`;
- manifest для каждого результата с hashes, commit SHA, seed, параметрами и версиями;
- публикация DRAT-файлов и/или LRAT, если размер позволяет, либо ссылка на архив с хешами.

Это не бюрократия: это снизит риск повторять дорогие вычисления и сделает результат пригодным для стороннего аудита.

### Фаза 2. Нормали сначала, offsets — сразу после

Текущий Q1 нужно развить в массовый эксперимент:

1. Для нескольких типов (58, 0, 11, затем типы с наилучшими combinatorial chain properties) генерировать много разнообразных chain-consistent normal sets.
2. Для каждого набора проверять точные degrees по уровням и точные saddle counts.
3. Глобальное covering пока помечать как sampled unless/until exact proof exists.
4. Сразу после генерации решать M0 exact offsets SMT.
5. Если M0 SAT, сохранять точную поверхность и идти на M1; если UNSAT, фиксировать первый невозможный уровень.
6. Повторять много раз на разных нормалях, чтобы получить статистику, а не один случай.

**Основной новый сигнал:** не только «нашли ли допустимые нормали», но «какой доле Gauss-admissible нормальных наборов удаётся пройти exact offset stage и где чаще всего появляется первое UNSAT».

Важная рекомендация: добавить условия sphere closure / period equations и face simplicity в outer-normal search, чтобы не генерировать нормали, заведомо несовместимые уже с M0.

### Фаза 3. Разобрать локальную теорию immersion

Это направление потенциально может превратить вычислительные наблюдения в короткие теоремы.

- Формализовать ограничение «не более одного reflex corner на вершину» и доказать его для полигонального immersion с degree-3 вершинами.
- Вывести локальные следствия для каждого 11-угольника и для пар соседних граней.
- Исследовать parity/crossing count ограничения; не называть их теоремами, пока нет полного доказательства.
- Собирать минимальные UNSAT cores для симметричных инстансов; искать человеческие геометрические леммы, объясняющие конфликт.
- Попробовать face-by-face decomposition по rank-3 contractions, как намечено в proof-roadmap.

Если асимметричный immersion UNSAT хотя бы для значительной части типов, это может сильно сузить глобальную задачу.

### Фаза 4. Сопоставить SAT-подходы и договориться о независимой проверке

Связаться с авторами `polyhedraproof` с конкретным предложением:

- сравнить редукцию к 59 формулам с вашим 715-sign OM-SAT и face-plane chirotope encoding;
- проверить, какие из ваших локальных clauses/lemmas уже входят в их формулы;
- предоставить один-два независимо сверенных эталонных map instances;
- обменяться проверками soundness, а не только runtime;
- совместно определить небольшой challenge set: пара симметричных UNSAT-кейсов, один асимметричный hard instance, Szilassi positive control и Röst–Vígh doubled-edge control.

Не запускать сотни core-hours, пока не понятно, какие конкретно новые данные даст этот запуск по сравнению с уже опубликованным pilot.

### Фаза 5. Контрольные эксперименты на 8 гранях

Восьмигранные genus-3 объекты дают хороший промежуточный benchmark, но двойные смежности должны поддерживаться как отдельный combinatorial type: dual map — мультиграф, а не простой граф.

Перед переносом Gauss machinery на эту постановку нужно:

- реализовать corner-based orientation с повторяющимися соседями;
- проверить degree = −2 на обоих опубликованных восьмигранных примерах;
- включить Mizhaev как второй positive control;
- проверить genus-2 rung вашего n=8 поиска и определить, обусловлен ли его plateau неверным Gauss-классом.

### Финальный вердикт

**Продолжать — да. Продолжать прежним способом — нет.**

Проект уже имеет содержательные результаты, которые не исчезают даже если genus-6 объекта не существует. Самое важное достижение последних дней — понимание, что предыдущий genus-4 plateau был не просто недостатком вычислительной мощности: поисковая схема попадала в неправильный класс нормалей. Это качественный научный сдвиг.

Но теперь требуется дисциплина следующего уровня: каждый крупный эксперимент должен проверять конкретную гипотезу, иметь заранее сформулированный критерий успеха/опровержения и завершаться точным свидетельством или корректно ограниченным отрицательным выводом.

Я бы выделил ближайший исследовательский бюджет не на ещё один длительный «поиск рода 6», а на:

1. закрытие reproducibility gaps;
2. массовый Q1 normals-first + exact offsets с несколькими типами и многими seeds;
3. локальные immersion obstructions и минимальные UNSAT cores;
4. независимое сопоставление с `polyhedraproof` и внешний математический review.

После этих этапов можно будет принимать осмысленное решение: идти в кластерный SAT-proof campaign, менять класс геометрических Ansatz или публиковать отдельный промежуточный результат.

## 15. Являются ли найденные genus-3 поверхности новыми объектами типа Мизаева?

### 15.1. Нет — в текущем виде это не многогранники Мизаева

В работе Руслана Мизаева описана поверхность рода 3 с **8** простыми планарными девятиугольными гранями. Каждая пара из восьми граней имеет хотя бы одно общее ребро: 20 пар имеют по одному ребру, а 8 пар — по два коллинеарных ребра. Это именно восьмигранный pairwise-adjacent объект (с оговоркой о кратных соседствах), а не просто поверхность рода 3 с несколькими соседствующими гранями. Работа: https://arxiv.org/abs/2609.17700.

У проекта Polyhedrons другая конструкция:

- 12 граней, а не 8;
- 32 вершины и 48 рёбер;
- 48 из 66 возможных пар граней имеют общее ребро;
- 18 пар граней пока не соседствуют.

Поэтому эти объекты нельзя называть новыми «многогранниками Мизаева», новыми 12-гранными neighborly polyhedra или решениями исходной задачи. Для строгого целевого свойства не хватает 18 соседств.

### 15.2. Но `type0_genus3_extendable` — не случайный промежуточный объект

Здесь важно различать два семейства, которые в раннем резюме были объединены слишком общо.

**Семейство A — `genus_ladder/type0_genus3_extendable*.json`.** Это точные вложения одного и того же комбинаторного типа рода 3. Для него вычислитель `reach()` находит достижимость всех 66 пар соседств последовательностью трёх добавлений ручек. Иными словами, его абстрактная карта является настоящим промежуточным уровнем одной из комбинаторных цепочек, ведущих к genus-6 целевой карте. В журнале проекта это отдельно отмечено как первый genus-3 объект, который не является combinatorial dead end.

Это существенно сильнее, чем «нашли красивую поверхность с 48 соседствами»: уже построена геометрически корректная реализация именно той карты, которую можно топологически продолжить до целевого combinatorial map.

**Однако геометрическое продолжение не найдено.** Комбинаторное добавление трёх ручек не доказывает, что конкретное вложение в `R^3` можно продолжить, сохраняя простоту граней и отсутствие пересечений. Более того, найденный Gauss-degree анализ показывает препятствие для прямого продолжения сохранённых конфигураций с фиксированными нормалями.

Сохранённые пять JSON-файлов — это пять геометрических конфигураций/вариантов одного и того же abstract map, а не пять новых комбинаторных типов. Полированная версия также является вариантом исходной реализации; число файлов нельзя выдавать за число доказанно неэквивалентных геометрических объектов.

**Семейство B — `solid_first/genus3_12faces_48pairs*.json`.** Это отдельное точно проверенное вложение рода 3, с другой комбинаторной картой. Но `handle_add.py`/`reach()` относит такие solid-first карты к тупиковым: для данного объекта достижимое число соседств не достигает 66 (в ночном отчёте для genus-3 solid-first карт указан максимум 54). Поэтому его ценность для прямого решения исходной задачи ниже. Он всё ещё полезен как самостоятельный тестовый объект для геометрического валидатора, solid-first поиска и анализа препятствий.

### 15.3. Самостоятельная ценность этих объектов

У семейства A есть четыре конкретных применения:

1. **Геометрическая опорная точка для целевой комбинаторики.** Это известный проекту точный embedded base case на пути к genus 6. Теперь вопрос можно формулировать не как поиск с нуля, а как поиск допустимого геометрического перехода через очередную ручку.
2. **Положительный benchmark.** Конфигурации проверяют face-plane construction, точную арифметику, простоту граней, отсутствие лишних пересечений, вычисление Gauss degree и извлечение карты.
3. **Лаборатория пространства реализаций.** Несколько геометрических вариантов одной карты дают материал для изучения chirotope chambers, вырождений, связности пространства реализаций и возможных переходов между камерами.
4. **Контрольная задача для новых методов.** Любая новая система поиска должна уметь заново получить или хотя бы точно верифицировать этот объект, прежде чем её применять к гораздо более трудному genus-6 случаю.

У семейства B основная полезность сейчас методическая: положительный exact-embedding test и пример того, как геометрически корректный объект может оказаться комбинаторным тупиком относительно конкретного целевого свойства.

**Новизна:** текущая проверка показывает, что эти карты отличаются от конкретной известной регулярной карты Dyck `{8,3}` (у неё 12 восьмиугольных граней) и от опубликованных восьмигранных объектов Мизаева и Röst–Vígh. Но это ещё не означает, что они являются новыми combinatorial maps или первыми геометрическими реализациями такого рода. В литературе существуют и другие абстрактные genus-3 карты с 12 восьмиугольными гранями, в том числе нерегулярные варианты. Нужна отдельная проверка каталогов карт и геометрических реализаций до заявления о приоритете.

## 16. Q1: закреплённый научный вывод

Эксперимент Q1 следует считать одним из центральных результатов последнего исследовательского цикла, а не просто неудачным запуском solver-а.

Для типа 58 была найдена система из 12 нормалей, которая проходит точные проверки требуемой последовательности степеней Гауссова отображения на всех уровнях:

\[
(D_0,D_1,\ldots,D_6)=(1,0,-1,-2,-3,-4,-5).
\]

Но после фиксации этой системы нормалей точная SMT-задача на смещения плоскостей для нижнего уровня — сферы рода 0 — оказалась `UNSAT`.

### 16.1. Что эксперимент действительно установил

Он опровергает более сильную гипотезу:

> «Если набор нормалей проходит все Gauss-degree проверки, то можно подобрать смещения плоскостей, реализующие нужную поверхность».

Эта гипотеза неверна: прохождение Gauss-degree gate не гарантирует даже существования базовой сферической геометрии для выбранного набора нормалей.

Отсюда следует, что Gauss-degree — необходимый фильтр, но не достаточное условие. Между нормалями и смещениями существует ещё слой совместимости, который должен учитывать как минимум замыкание граней, существование правильных областей граней, простоту многоугольников и отсутствие нежелательных пересечений.

### 16.2. Чего эксперимент не установил

`UNSAT` относится к одной найденной системе нормалей типа 58, конкретному gauge и конкретной закодированной задаче смещений. Это не доказывает:

- невозможность всех систем нормалей типа 58;
- невозможность genus-0 base realization для всех карт;
- невозможность genus 6;
- недостаточность Gauss map как математического метода вообще.

Перед дальнейшим масштабированием Q1 необходимо получить минимальный UNSAT core (если solver его поддерживает для данной формулы), проверить его независимым способом и попытаться перевести конфликт в геометрическое условие, понятное без Z3.

### 16.3. Следующий правильный вопрос

Не «сколько ещё нормалей нужно случайно сгенерировать?», а:

> Какие дополнительные инварианты нормальной конфигурации, помимо степени Гауссова отображения, необходимы для существования совместимой системы смещений уже на сфере?

Это и есть содержательный научный выход Q1. Следующий эксперимент должен либо выявить компактное дополнительное условие, либо показать, что offset-feasibility сильно зависит от конкретной камеры нормалей. Большой случайный перебор без анализа UNSAT-причины не является приоритетом.

## 17. Обновлённая стратегия: искать не всё пространство, а информативные области

Автор проекта явно выбирает ресурсно-осознанную исследовательскую стратегию: один ноутбук не способен исчерпывающе перебрать всё пространство геометрических вариантов, поэтому преимущество проекта должно быть не в количестве CPU-часов, а в выборе редких, математически мотивированных областей поиска.

Это становится основным принципом дальнейшей программы:

**Сначала теория и дешёвый фильтр → затем эксперимент с высокой различающей способностью → затем точный solver → затем обобщение результата в лемму.**

Каждый дорогой запуск должен быть оправдан тем, что его исход различает конкурирующие гипотезы. До запуска фиксируются:

- математическая гипотеза;
- какие результаты её подтвердят или опровергнут;
- почему выбран именно этот тип/камера нормалей/класс конфигураций;
- минимальный пилот, который может быстро выявить ошибку идеи;
- критерий остановки;
- что будет извлечено из `SAT`, `UNSAT`, timeout и найденного near-miss.

Timeout нельзя записывать как отрицательный математический результат; `UNSAT` нельзя обобщать за пределы точной формулы; красивый near-miss не считается прогрессом без проверки вырождений.

### 17.1. Перенос методов из смежных областей

Предлагаю не распыляться на десятки экзотических идей, а проверить четыре междисциплинарных переноса.

**A. Configuration-space planning из робототехники.**

Пространство геометрических реализаций можно рассматривать как конфигурационное пространство: допустимые конфигурации — свободная область, нулевая длина ребра, касание/пересечение граней и потеря простоты — препятствия/границы. Вместо локального спуска по одной energy function можно исследовать структуру допустимых областей и переходы между ними методами motion planning, roadmap и continuation. Вопрос становится таким: находятся ли genus-3 и потенциальные genus-4 реализации в одной компоненте допустимого пространства или переход требует пересечения дискриминантного множества?

Проверка должна быть сначала малой: построить path/roadmap только в пространстве реализаций одного genus-3 map и проверить, какие геометрические свойства сохраняются. Не следует заранее считать, что RRT/PRM автоматически решат задачу: это кандидат на метод исследования связности, не готовое решение.

**B. Oriented matroids и arrangement chambers.**

Нормали/коэффициенты плоскостей разбивают пространство на камеры, в которых набор знаков определителей (chirotope) постоянен. Пять найденных вариантов одного type-0 map — материал для изучения того, какие камеры реально реализуют эту карту. Вместо равномерного случайного семплирования координат можно искать соседние камеры, переходы через одну вырожденную гиперповерхность и инварианты, которые запрещают целые семейства камер.

**C. Proof mining из UNSAT cores и SAT-сертификатов.**

Использовать SAT/SMT не только как «машину ответа», но как инструмент открытия лемм. Извлекать минимальные или малые конфликтующие наборы ограничений, переводить их в геометрические утверждения, искать общую причину для нескольких карт и затем доказывать эту причину независимо от solver-а. Цель — заменить тысячи конкретных перебранных вариантов одной компактной леммой.

**D. Rigidity theory / stress methods.**

Изучить матрицы ограничений и ранги для системы плоскостей, вершин и условий замыкания. Возможный путь — обнаружить неизбежную линейную зависимость («stress») или ранг-дефект, который мешает одновременно выполнить замыкание, ориентацию и простоту. Это потенциальный способ вывести быстрый necessary condition до запуска нелинейного SMT.

Эти переносы ранжируются по близости к имеющимся данным: сначала B и C (поскольку проект уже располагает chirotope/SAT/SMT-артефактами), затем A и D как более новые теоретико-алгоритмические направления.

### 17.2. Как выбирать эксперименты

Предлагается оценивать каждый следующий эксперимент по пяти критериям от 0 до 2:

1. **Теоретическая мотивация:** есть ли вывод из леммы/инварианта, а не только интуиция?
2. **Различающая способность:** разные исходы действительно меняют исследовательскую программу?
3. **Дешёвый falsification test:** можно ли быстро опровергнуть идею на малом примере?
4. **Потенциал обобщения:** может ли результат стать леммой для многих типов?
5. **Воспроизводимость:** будет ли результат точным, архивируемым и повторяемым?

Не запускать дорогой эксперимент с низким баллом по теоретической мотивации и различающей способности, даже если его легко распараллелить.

## 18. Один приоритетный результат для первого AI-assisted research note

В качестве первого компактного результата для глубокого анализа с помощью ИИ выбираю не симметричный UNSAT (он уже имеет близкую независимую публикацию) и не единичный Q1 `UNSAT` (сам по себе он пока слишком узок), а:

> **Точную genus-3 реализацию типа `type0`, комбинаторно продолжаемого до одной из целевых neighborly genus-6 карт.**

Это наиболее понятный положительный результат: есть геометрический свидетель, точный верификатор, известная комбинаторная карта и проверяемая последовательность ручек, которая доводит её до 66 соседств.

### 18.1. Предварительная формулировка результата

Существует замкнутая ориентируемая полигональная поверхность рода 3 в \(\mathbb R^3\), состоящая из 12 простых плоских граней, с 32 вершинами и 48 рёбрами, причём 48 пар граней имеют по одному общему ребру. Её комбинаторная карта допускает продолжение тремя handle attachments до целевой genus-6 карты с 66 соседствами.

Это пока **не** утверждение о геометрическом продолжении и **не** заявление о новом многограннике Мизаева. Термин «новая» можно использовать только после проверки новизны карты и геометрической реализации по каталогам и литературе.

### 18.2. Почему этот результат подходит для первого AI-аудита

- У него ограниченный, самодостаточный набор исходных файлов.
- Математическое утверждение позитивное и не зависит от интерпретации длинных оптимизационных запусков.
- Можно построить независимый checker, не полагаясь на один авторский скрипт.
- Комбинаторную часть можно проверить канонизацией карты и явным перечнем трёх добавляемых ручек.
- Новизну можно исследовать отдельно от корректности: сначала доказать объект, затем сравнить с известными картами.

### 18.3. Задание для ИИ-агента

1. Взять `type0_genus3_extendable.json` и четыре его варианта; не читать только обзорные README.
2. Независимо восстановить циклические обходы 12 граней и точные рациональные координаты всех вершин из рационализированных плоскостей.
3. Второй реализацией проверить замкнутость, ориентируемость, простоту всех граней, ровно заданные попарные пересечения, отсутствие самопересечений и \(\chi=-4\).
4. Канонизировать abstract map; проверить, что все сохранённые варианты принадлежат одному map type, и не выдавать их за разные комбинаторные типы.
5. Независимо проверить `reach=66` и выписать ровно три handle attachments, ведущих к целевой карте.
6. Сравнить карту с известными genus-3 maps, включая Dyck map `{8,3}` и нерегулярные карты из каталогов; отдельно искать известные геометрические реализации в \(\mathbb R^3\).
7. Выдать короткий referee-style dossier: точная теорема, полный набор сертификатов, novelty assessment, ограничения утверждения и список вопросов внешнему математику.

**Критерий успеха:** не «ИИ написал статью», а получен независимый, компактный и проверяемый пакет, на основе которого математик может за короткое время оценить корректность и новизну.

## 19. GitHub Actions как вычислительная лаборатория

Идея запускать каждый эксперимент в отдельной ветке как вычислительный workflow технически реализуема. GitHub Actions не ограничивает workflow только тестами: `run:` может запускать Python, C++, SAT/SMT solvers и любые другие допустимые вычислительные программы.

Для публичного репозитория стандартные GitHub-hosted runners бесплатны; текущая документация GitHub указывает, что для публичных репозиториев standard runners доступны бесплатно и без включённого месячного лимита минут. Для публичного `ubuntu-latest` сейчас заявлен runner с 4 CPU, 16 GB RAM и 14 GB SSD. Это может дать заметно больше параллельного CPU, чем один ноутбук, хотя это не HPC-кластер и ресурсы одного job ограничены.

### 19.1. Практические ограничения на 31 октября 2026 г.

| Ограничение | Текущее значение | Значение для проекта |
|---|---:|---|
| Максимальная длительность одного GitHub-hosted job | 6 часов | Длинный поиск нужно делать checkpoint/resume или разбивать на стадии |
| Максимальная длительность workflow run | 35 дней | Несколько jobs могут образовать длинный experiment pipeline, но каждый job всё равно ограничен 6 часами |
| Матрица | 256 jobs на один workflow run | Удобно распараллелить seeds / типы / конфигурации |
| Одновременно запущенные standard jobs на GitHub Free | 20 | В идеале это до 20 параллельных независимых задач; Pro — 40, по текущей таблице GitHub |
| Максимальный retention для публичного репозитория | 90 дней | Артефакты и логи нельзя считать постоянным архивом доказательств |
| Размер стандартного публичного Ubuntu runner | 4 CPU, 16 GB RAM, 14 GB SSD | Подходящий baseline для CPU-bound Python/SAT задач; мало диска для больших proof archives |
| Максимальный размер матрицы | 256 jobs | Для большего числа seeds нужны пакетные workflow runs |

Указанные лимиты изменяемы GitHub; при росте проекта следует сверять актуальную страницу Actions limits.

### 19.2. Как запускать вычисления из отдельных веток

Для `push` GitHub может запустить workflow, который присутствует в pushed branch, даже если файл workflow ещё не влит в default branch. Поэтому экспериментальная ветка `experiment/q1-offsets` может содержать свой `.github/workflows/run-experiment.yml` и запускаться при push.

Но удобнее поддерживать **один общий runner workflow** в default branch, а каждый эксперимент описывать отдельной веткой и конфигурацией:

- `experiment/q1-type58-offsets` — конфиг, hypothesis, параметры и код конкретного эксперимента;
- `experiment/gauss-chambers-type0` — другая гипотеза;
- workflow запускается на `push` для веток `experiment/**` или вручную через `workflow_dispatch`;
- для кнопки `Run workflow` workflow-файл должен быть в default branch; после этого можно выбирать ветку запуска.

Это сокращает копирование YAML, но сохраняет полную привязку результата к commit SHA эксперимента. Отдельный workflow-файл внутри branch тоже возможен, если нужен полностью автономный запуск.

### 19.3. Минимальный шаблон

Ниже пример общего workflow. В боевой версии нужно закрепить сторонние Actions полными commit SHA, а не только плавающими тегами. Параметры эксперимента следует хранить в version-controlled config-файле в соответствующей ветке.

```yaml
name: Research experiment

on:
  push:
    branches: ["experiment/**"]
    paths:
      - "research/**"
      - ".github/workflows/research-experiment.yml"
  workflow_dispatch:
    inputs:
      experiment:
        description: "Experiment/config id"
        required: true
        type: string

permissions:
  contents: read

jobs:
  compute:
    runs-on: ubuntu-24.04
    timeout-minutes: 350
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.ref }}

      - name: Record provenance
        run: |
          mkdir -p artifacts
          git rev-parse HEAD > artifacts/commit.txt
          python --version > artifacts/python-version.txt
          lscpu > artifacts/cpu.txt
          free -h > artifacts/memory.txt

      - name: Run experiment
        run: |
          python research/12-faced-polyhedron/code/run_experiment.py \
            --config research/12-faced-polyhedron/configs/${{ inputs.experiment }}.yaml \
            --output artifacts/result.json

      - name: Upload result
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: ${{ github.ref_name }}-${{ github.run_id }}
          path: artifacts/
          retention-days: 90
```

Путь/CLI в примере нужно адаптировать к реальному runner-скрипту проекта; это архитектурный шаблон, не готовый к запуску без такого entry point.

### 19.4. Что обязательно сохранять

Каждый запуск должен оставлять self-describing result package:

- commit SHA и имя ветки;
- конфиг эксперимента, все параметры и random seed;
- версии Python, библиотек, SAT/SMT solver-ов, контейнер/image digest;
- CPU/RAM runner-а;
- stdout/stderr и exit code;
- checkpoints и найденные модели/кандидаты;
- точный verifier output;
- хеши входов, результатов и сертификатов;
- короткий `CONCLUSION.md`: что гипотеза предсказывала, что произошло и что этот исход позволяет утверждать.

Большие proof files нужно переносить в versioned long-term archive (GitHub Release/Zenodo/другое устойчивое хранилище) и в Git оставлять URL, размер и SHA-256. Actions artifacts в публичном репозитории по текущей политике имеют максимум 90 дней хранения.

### 19.5. Предлагаемая схема экспериментов

Не создавать новую копию workflow на каждый random seed. Лучше:

- одна ветка на одну научную гипотезу/эксперимент;
- один config-файл на условие;
- матрица GitHub Actions — на независимые подзадачи (разные seed, карты, normal chambers);
- один job — одна воспроизводимая порция вычисления с жёстким timeout и checkpoint;
- отдельный артефакт на каждый job и итоговый агрегатор, который собирает таблицу результатов.

Использовать `concurrency`, чтобы случайные последовательные push не порождали бесконечные очереди. Для тяжёлых задач — регулярно сохранять checkpoint и запускать следующий batch с него. Не давать workflow права `contents: write`, если они не нужны; не запускать потенциально недоверенный код pull request с секретами. GitHub отдельно указывает, что использование Actions должно соответствовать GitHub Terms of Service и Additional Product Terms.

**Вывод:** GitHub Actions — разумный способ превратить репозиторий в небольшую распределённую вычислительную лабораторию: запускать множество независимых, ограниченных и воспроизводимых экспериментов на облачных runner-ах. Но это не замена математическому отбору гипотез. Приоритет остаётся за экспериментами, которые проверяют одну сильную идею, а не за максимальным количеством случайных стартов.

## 20. Обновлённый главный вывод аудита

Проекту следует продолжать исследование, но измерять прогресс количеством новых доказательных ограничений, а не CPU-часами и числом запусков.

На ближайшем этапе наиболее ценно:

1. разобрать Q1 через UNSAT core и попробовать получить человеческую геометрическую лемму о несовместимости нормалей и смещений;
2. использовать `type0_genus3_extendable` как основной exact positive control и исследовать геометрическую возможность перехода от него к следующему genus;
3. изучить пространство chirotope chambers и искать переходы/обструкции не в сырых координатах, а на уровне камер;
4. превратить небольшие вычислительные конфликты в компактные геометрические леммы;
5. использовать GitHub Actions для воспроизводимых и параллельных экспериментов, каждый из которых проверяет заранее сформулированную гипотезу.

**Новый критерий исследовательского успеха:** один хороший эксперимент должен либо найти точный свидетель, либо дать независимый сертификат невозможности, либо выявить короткую причину неудачи, которую можно превратить в общее утверждение. Если он лишь увеличивает число просмотренных конфигураций, его приоритет низкий.

# Addendum от 31 октября 2026: уточнения после обсуждения с автором

## 21. Уточнение: являются ли найденные genus-3 конструкции новыми объектами типа Мизаева?

Нет, их нельзя называть многогранниками Мизаева или новыми реализациями его восьмигранного объекта.

В работе Р. Мизаева (arXiv:2609.17700, 15 сентября 2026) дан genus-3 объект с 8 простыми планарными девятиугольными гранями, 24 вершинами и 36 рёбрами. Каждая пара граней соседствует; 20 пар имеют одно общее ребро, 8 пар — два коллинеарных общих ребра. В Polyhedrons построены другие объекты: 12 граней, 32 вершины, 48 рёбер, genus 3 и 48 соседствующих пар из 66.

Обе `solid-first` реализации повторно проверены `verification/verify_solid.py`: `EXACT_EMBEDDED=True`, 12 простых граней, `chi=-4`, `genus=3`, `V=32`, `E=48`, 48/66 смежных пар и пустой список лишних пересечений. Все пять файлов `type0_genus3_extendable*.json` повторно прошли `ladder_exact.verify`.

Распределения числа сторон граней (они же степени вершин dual face-adjacency graph) различаются:

- type0: `6, 6, 6, 6, 8, 8, 9, 9, 9, 9, 10, 10`;
- solid-first: `5, 6, 7, 7, 8, 8, 8, 8, 9, 9, 10, 11`.

Следовательно, эти две карты различны. Обе отличаются и от конкретной регулярной карты Dyck `{8,3}` / dual R3.2, для которой все 12 граней восьмиугольные. Однако это пока не доказательство международной новизны: необходимо проверить полные каталоги genus-3 maps, канонизировать карты с учётом перестановок граней и зеркального обращения и поискать известные пространственные реализации. До завершения этой проверки корректная формулировка — «новые для проекта точно проверенные конструкции», а не «первые в мире».

Их самостоятельная ценность:

1. точные положительные benchmark-объекты для plane-arrangement/solid-first генераторов и геометрических валидаторов;
2. примеры разных genus-3 карт с одинаковым f-вектором `(V,E,F)=(32,48,12)`;
3. материал для исследования пространства геометрических реализаций: журнал фиксирует несколько chirotope-различающихся реализаций одной type0 карты;
4. для type0 — конкретный геометрически реализованный нижний уровень одной комбинаторной цепочки, ведущей к целевой карте genus 6.

Не следует считать пять JSON пятью разными абстрактными картами. Они являются пятью геометрическими реализациями одного type0 combinatorial map. Отличающиеся chirotope/sign-patterns могут быть интересны для изучения камер пространства реализаций, но сами по себе ещё не доказывают различные ambient-isotopy classes.

## 22. Уточнённый результат Q1: chain-consistent normals не решают задачу смещений

Эксперимент `chain_normals.py` дал важный частичный положительный результат. Для type 58 и chain seed 3 найден один набор из 12 нормалей, который одновременно проходит точные проверки требуемых Gauss-классов на всех семи уровнях:

`M0, M1, ..., M6`: степени `+1, 0, -1, -2, -3, -4, -5`.

Затем при фиксации этих нормалей точная Z3/SAT-модель для смещений плоскостей самого нижнего уровня `M0` (сфера) вернула `UNSAT` за 33 секунды.

**Правильная интерпретация:** Gauss-degree admissibility — необходимый фильтр, но для данной найденной системы нормалей он не является достаточным условием существования геометрической реализации. Отдельно требуется обеспечить совместимость смещений/периодов, замыкание граней, правильную комбинаторику и простоту полигонов. Q1 тем самым указал, какой слой условий отсутствует в текущем normals-first фильтре.

**Граница вывода:** этот `UNSAT` относится к конкретному набору нормалей, gauge, bounds/margins и текущей формализации offset feasibility. Он не доказывает, что для type 58 не существует другой подходящей системы нормалей, не опровергает normals-first стратегию и тем более не доказывает невозможность исходного genus-6 объекта. В bundle не обнаружен сохранённый SMT2/proof/UNSAT-core для этого конкретного прогона; результат пока является точным ответом solver-а на зафиксированную модель, но не независимым доказательным сертификатом.

Следующий научный шаг — не массово перебирать новые normals seeds, а извлечь малое ядро противоречия для найденного seed, перевести его в понятное геометрическое утверждение и проверить, какая именно связь между нормалями и смещениями нарушена. Затем нужно изменить prefilter так, чтобы offset/period feasibility проверялась дешево раньше более дорогих стадий.

## 23. Новый проверяемый артефакт: явная цепочка genus 3 → genus 6 на комбинаторном уровне

В ходе повторной проверки `type0_genus3_extendable.json` была не только подтверждена запись `reach=66`, но и извлечена конкретная последовательность трёх handle attachments. Каждая операция удаляет две непересекающиеся треугольные грани двойственной триангуляции и добавляет шеститреугольную annulus-полоску, внося шесть новых рёбер (то есть шесть новых пар соседних исходных граней).

Явные пары удаляемых треугольников:

1. `(1,2,10)` и `(4,7,9)`;
2. `(0,5,8)` и `(2,6,7)`;
3. `(0,9,11)` и `(3,5,10)`.

Сохранён полный список шести вставляемых треугольников и шести новых смежностей на каждом шаге в файле `polyhedrons_type0_handle_completion_certificate.json`. Уровни проверены по точным дискретным инвариантам:

| Уровень | Dual triangles | Edges / face adjacencies | Euler characteristic | Genus |
|---|---:|---:|---:|---:|
| M3 | 32 | 48 | −4 | 3 |
| M4 | 36 | 54 | −6 | 4 |
| M5 | 40 | 60 | −8 | 5 |
| M6 | 44 | 66 | −10 | 6 |

Для всех четырёх карт проверено: каждая дуальная грань-треугольник имеет три различных вершины; каждое ребро принадлежит ровно двум треугольникам; dual-graph связен; link каждой вершины является одним циклом; существует согласованная ориентация. Финальная карта при текущей нумерации вершин совпадает с записью `id=0` в `data/k12_triangulations.json`.

Воспроизводимый независимый проверяющий скрипт — `verify_type0_handle_completion.py`. Его успешный вывод подтверждает только **комбинаторное** продолжение. Никакая геометрическая реализация уровней genus 4, 5 или 6 этим сертификатом не заявляется.

Этот извлечённый witness делает type0 результат заметно сильнее и удобнее для внешнего ревью: теперь вместо утверждения «reach сообщает 66» можно предоставить конечный объект, три операции и проверку каждого промежуточного уровня.

## 24. Приоритетный результат для первого AI-assisted research dossier

Выбирается один результат:

> **Точная genus-3 пространственная реализация type0-карты, для которой предоставлена явная комбинаторная цепочка трёх handle attachments до одной из 59 целевых genus-6 триангуляций.**

Почему он предпочтительнее для первого AI-ревью:

- позитивный и математически конкретный результат, а не интерпретация большого массива failed runs;
- малый набор данных: 12 рационализируемых плоскостей, 32 треугольника двойственной карты, 3 surgery и 4 конечные карты;
- геометрическая часть genus 3 проверяется точной арифметикой;
- комбинаторное продолжение можно независимо проверить коротким скриптом;
- корректность и новизну можно исследовать раздельно.

AI-задача должна быть ограничена referee-style проверкой: (i) независимая проверка rationalized geometry genus 3, (ii) канонизация исходной карты, (iii) проверка каждого из трёх handle surgeries, (iv) сверка final map с каталогом 59, (v) novelty search по genus-3 maps и polyhedral embeddings, (vi) точная формулировка того, что доказано и чего не доказано. Не просить ИИ сразу «написать статью».

Q1 следует выделить как отдельную следующую исследовательскую задачу — proof mining из offset-UNSAT, — но не выбирать его первым внешним результатом, пока нет сохранённой формулы и объяснимого ядра противоречия.

## 25. Уточнённая исследовательская философия: не полный перебор, а поиск с высокой информационной отдачей

Авторская стратегическая установка становится явным принципом проекта:

**Не пытаться перебрать всё пространство вариантов. Искать математически мотивированные, неочевидные подпространства и методы, в которых небольшой эксперимент способен исключить целый класс конфигураций или открыть новое ограничение.**

Каждая новая идея должна проходить короткий decision protocol:

1. **Математический источник:** какое известное свойство, инвариант, лемма или структура подсказывает направление?
2. **Перенос метода:** есть ли полезная аналогия из другой дисциплины?
3. **Различающий эксперимент:** какие разные гипотезы разделяют исходы теста?
4. **Дешёвое опровержение:** можно ли сначала проверить идею на малой конфигурации или одном seed?
5. **Путь к лемме:** если тест сработает/не сработает, можно ли получить обобщаемое утверждение, сертификат или короткое объяснение?

Идеи для переноса, приоритетно связанные с текущими данными:

- **Proof mining / SAT-core analysis:** использовать малые UNSAT cores не только как результат solver-а, а как источник геометрических лемм; выявлять повторяющиеся минимальные конфликты для целых семейств.
- **Теория камер oriented matroids и arrangement geometry:** исследовать соседство камер/chirotope, границы вырождения и возможные переходы между реализациями вместо равномерного семплирования пространства нормалей.
- **Motion planning из робототехники:** рассматривать множество допустимых вложений как configuration space, а вырождения (нулевые рёбра, касания, самопересечения, потеря простоты) как препятствующий дискриминант. Построить небольшой roadmap пространства реализаций genus 3 и выяснить, можно ли выйти в область, где следующая ручка реализуема, не пересекши запрещённую границу.
- **Rigidity theory / stress matrices:** изучать ранг якобиана условий замыкания и планарности, infintesimal motions и самонапряжения. Возможный успех — раннее ранговое препятствие, исключающее семейство offset-систем до запуска нелинейного поиска.
- **Active learning / experimental design:** выбирать следующий эксперимент по ожидаемой информационной ценности: насколько каждый возможный исход изменит стратегию? Сначала максимизировать различающую способность, а не число seeds/CPU-hours.
- **Homotopy continuation и алгебраическая геометрия:** при переходе между уровнями пытаться отслеживать ветви решений параметризованной системы и ловить точку входа в дискриминант, вместо независимых перезапусков оптимизатора.

Эти идеи — не утверждения, что соответствующие инструменты автоматически решат задачу. Это конкретные междисциплинарные гипотезы, каждая из которых должна быть проверена дешёвым тестом и иметь понятный критерий успеха.

## 26. GitHub Actions: уточнённая архитектура и проверенные лимиты

Идея автора технически корректна: GitHub Actions может выполнять полноценные научные вычисления, а не только unit tests. В workflow можно запускать Python/C++, SAT/SMT, CP-SAT, exact verifiers и скрипты анализа. `push`-событие может запускать workflow, определённый прямо в экспериментальной ветке; GitHub использует workflow-файлы, присутствующие в commit/ref соответствующего события. `workflow_dispatch` имеет отдельное правило: workflow-файл должен присутствовать в default branch, чтобы ручной trigger был доступен.

На 31 октября 2026 года официальная документация GitHub указывает:

- standard Linux runner `ubuntu-24.04`/`ubuntu-latest` для публичного репозитория: 4 CPU, 16 GB RAM, 14 GB SSD; standard GitHub-hosted runner usage для public repo бесплатен без лимита минут;
- максимальная одновременность standard hosted jobs: GitHub Free — 20, Pro — 40 (лимит плана аккаунта, не на одну ветку);
- каждый hosted job — максимум 6 часов;
- весь workflow run — максимум 35 дней;
- matrix — максимум 256 jobs на один workflow run;
- для public repositories retention checks/runs/artifacts/logs ограничен 90 днями; начиная с 1 октября 2026 retention setting также охватывает check runs/workflow runs/statuses.

Эти ресурсы удобны для независимых CPU-задач: например, разные типы карт, normal chambers или семена после теоретически обоснованного отбора. Они не превращают несколько runner-ов в одну большую shared-memory машину: один job остаётся ограниченным 4 CPU и 16 GB RAM, а локальное состояние между jobs не сохраняется автоматически.

Рекомендуемая схема:

- одна ветка `experiment/<hypothesis-id>` на одну научную гипотезу;
- в ветке — формулировка гипотезы, config, код и commit SHA;
- один общий workflow для всех веток `experiment/**` (или отдельный файл в каждой ветке, если нужен полный экспериментальный capsule);
- матрица jobs только для действительно независимых подзадач;
- каждый job ограничен `timeout-minutes: 350` и пишет checkpoint;
- сохранять конфиг, seed, commit SHA, версии solver-а, runner specs, stdout/stderr, выходной статус, кандидаты, точный verifier report и SHA-256;
- Actions artifacts использовать для промежуточного обмена, но долгосрочные proof artifacts переносить в GitHub Release/Zenodo/долговременный архив, поскольку retention не постоянен;
- `GITHUB_TOKEN` с минимальными правами, не запускать недоверенный PR-код с секретами, не выдавать `contents: write`, если workflow не должен коммитить результаты.

Не надо запускать тяжёлый поиск на каждый push по умолчанию. Лучше push запускает быстрый smoke/preflight, а длинные эксперименты — вручную или только по явному экспериментальному branch/config. Для долгих вычислений разбивать работу на checkpointable jobs короче шести часов. Для независимых jobs можно ограничить `strategy.max-parallel` и использовать `concurrency`, чтобы не копить бесполезную очередь.

Предыдущий YAML-пример в основном отчёте следует рассматривать как архитектурный набросок, не как готовый workflow: в нём `inputs.experiment` используется для `push`, где такого input нет. Практичнее держать фиксированный config-файл в каждой experiment branch (например, `research/12-faced-polyhedron/experiment.yaml`) или явно вычислять config path из имени ветки.

Пример более согласованного шаблона (команда `run_experiment.py` здесь условная — её нужно реализовать как единый entry point проекта):

```yaml
name: Research experiment

on:
  push:
    branches: ["experiment/**"]
    paths:
      - "research/12-faced-polyhedron/**"
      - ".github/workflows/research-experiment.yml"
  workflow_dispatch:

permissions:
  contents: read

jobs:
  compute:
    runs-on: ubuntu-24.04
    timeout-minutes: 350
    strategy:
      fail-fast: false
      max-parallel: 4
      matrix:
        seed: [11, 12, 13, 14]
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.sha }}

      - name: Capture provenance
        run: |
          mkdir -p artifacts
          echo "$GITHUB_SHA" > artifacts/commit.txt
          echo "${{ github.ref }}" > artifacts/ref.txt
          echo "${{ matrix.seed }}" > artifacts/seed.txt
          python --version > artifacts/python-version.txt
          lscpu > artifacts/cpu.txt
          free -h > artifacts/memory.txt

      - name: Run one bounded experiment
        run: |
          python research/12-faced-polyhedron/code/run_experiment.py \
            --config research/12-faced-polyhedron/experiment.yaml \
            --seed "${{ matrix.seed }}" \
            --output artifacts/result.json

      - name: Upload result package
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: ${{ github.ref_name }}-${{ matrix.seed }}-${{ github.run_id }}
          path: artifacts/
          retention-days: 90
```

Для `push` workflow может жить в experiment branch и запускаться до merge. Для ручного `workflow_dispatch` тот же workflow-файл должен также существовать в default branch; в UI выбирается нужная ветка. Один job — один seed/подзадача, а `max-parallel` ограничивает одновременный запуск внутри одной матрицы. При долгой работе checkpoint нужно писать периодически: нельзя рассчитывать, что жёстко завершённый на 6-часовом лимите job успеет выполнить последний upload step.

**Обновлённый главный вывод:** вычислительная мощность GitHub Actions способна помочь с параллельными независимыми проверками, но стратегия проекта должна оставаться theory-led. Облачные CPU следует тратить после математического отбора гипотез, не вместо такого отбора.
